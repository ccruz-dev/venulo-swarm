## The audit doesn't fully match the code

**G5 (calibration note):** half right.
- **The PDF is already fixed at generation time.** It is rendered once, in `server/workers/uploadWorker.js:262`, from `leakResults.calibration`, and saved as a file. Nothing re-renders it later.
- **The web page is the problem.** `server/routes/reports.js:640-658` rebuilds the note from the current venue profile every time the report is viewed.
- **Web and PDF disagree even without a profile change.** The web version uses different wording: it drops the price tier and the "normalized to a 30-day month from N day(s)" sentence that the PDF has (`server/services/leakEngine.js:2539`).

**G6 (backfill):** the description is wrong.
- **No check rejects old data.** Nothing in the code rejects data older than 28 days.
- **The 28-day limit is a cooldown per location.** It counts from the last successful report (`server/routes/uploads.js:234-259`), not from the age of the data.
- **The effect is what the audit describes.** A new customer can load one past month, then waits 28 days before loading the next, so trend features stay empty.

## Planned change: calibration snapshot (G5)

1. **Schema:** add a nullable `calibrationSnapshot String?` to `Report`. It holds JSON: the venue inputs (`venueType`, `venueLabel`, `priceTier`, `venueProfileSet`, `periodDays`) plus the finished note text.
2. **Migration:** `20260929000000_report_calibration_snapshot` would add the column. To undo it: `ALTER TABLE "Report" DROP COLUMN "calibrationSnapshot";`.
3. **Worker:** build the snapshot once from `leakResults`, pass its note to the PDF generator, and save the same snapshot on the report. Web and PDF would then always read one value.
4. **Web route:** read the note from `report.calibrationSnapshot` and never look up the venue profile.
5. **Older reports:** reports generated before this change have no snapshot, so the web page would show no calibration note. The alternatives are showing today's profile (the bug itself) or guessing. Their PDFs still carry the original note.
6. **Tests:**
   - In `reportTrust.test.js`: load a report with a snapshot, change the venue profile, load it again, and check the note is unchanged.
   - In `workerRecovery.test.js`: check that the note sent to the PDF matches the stored snapshot.

The shared-report route only returns a fixed list of fields, so the new column can't leak through share links.

## Planned change: backfill window (G6)

In `uploads.js`, skip the cooldown for **14 days after a location is created**, capped at **12 reports** (a year of monthly history). Both values would be named constants with a comment explaining them. The per-user upload rate limit of 3 per hour still applies. This doesn't open a new loophole: a brand-new location has no reports, so it already skips the cooldown today.

I'd also update the source-text checks in `uploadGate.test.js` to cover the new window.

## Decisions for you

- **Window and cap:** are 14 days and 12 reports acceptable?
- **Older reports:** is showing no calibration note on web for reports without a snapshot acceptable?
- **Upload order:** the worker compares each new report with the most recently *generated* report, not the previous *period*. Backfilling older months out of order would make those month-over-month findings misleading. I'd leave that out of this change.
- **Peer benchmark:** it still groups peers by the current venue type (`reports.js:593`). That isn't the calibration note, so I left it alone.
